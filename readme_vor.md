# README — Формирование ВОР по типовому шаблону (вкладка «Формирование ВОР»)

Документ описывает отдельный функционал сервиса — **формирование ведомости
объёмов работ (ВОР)** по типовому шаблону на основании цифровой модели здания
(IFC) и сопутствующих документов. Функционал доступен во вкладке
**«Формирование ВОР»** веб-интерфейса и не зависит от режимов ЦС/ИИ
(подбор работ здесь не выполняется — заполняются только объём и обоснование).

Вся логика сосредоточена в пакете [`src/services/vor_generation/`](./src/services/vor_generation).

---

## 1. Назначение

- Вход: **IFC-модель** (обязательно) и документы — **ВОР застройщика**,
  **ПОС**, **ПЗ**, **ПД** (необязательно; PDF/XLSX).
- Выход: заполненный файл **`Сформированный_ВОР.xlsx`** — копия типового
  шаблона `data/Типовой ВОР по КР.xlsx`, лист **«ВОР КР_ЖС»**, с сохранением
  структуры (части здания, разделы, подразделы, порядок и нумерация строк).
- Дополнительно, если загружен **PDF ВОР застройщика**, формируется файл
  **`ВОР_заказчика.xlsx`** — ВОР заказчика, приведённый к структуре типового
  ВОР (объёмы заказчика, сгруппированные по подразделам и частям здания
  шаблона; см. §4а).
- Заполняются столбцы:
  - **«Объем» (D)** — расчётный объём группы элементов модели (или найденное
    значение в документах, если в модели данных нет);
  - **«Обоснование объема работ» (F)** — ссылка на документ-источник
    («Модель IFC: …», «ВОР застройщика: …», «ПОС: …», «ПЗ: …», «ПД: …»).
- Подразделы, для которых данных нет, сохраняются **с прочерком** (столбцы D/F
  остаются пустыми).

## 2. Состав пакета `src/services/vor_generation`

| Модуль | Назначение |
|---|---|
| `mapping.py` | Правила сопоставления текстов типового ВОР с типами конструкций (`detect_kind`), частями здания (`detect_part`), геометрическими заголовками (`detect_geometry`), видами объёмов работ (`classify_work`) и ресурсов (`classify_resource`); разбор марок бетона (`parse_concrete_grade`, `parse_concrete_spec`, `concrete_label`) и спецификаций арматуры (`parse_rebar_spec`, `parse_thickness`, `rebar_bucket` — разделение «Арматура класса …» (стержни) и «Арматурные выпуски/каркасы …»); определение подтипа лестницы (`stair_component` — марш/площадка); сопоставление разделов ВОР застройщика с подразделами шаблона (`vor_section_matches` — тип конструкции + часть здания). Слово «сборные» трактуется как **технология, а не тип конструкции**: `precast` — только сборные **лестницы** (в модели — сборные лестничные марши), а прочие сборные изделия выделены в отдельные типы `precast_panel` (панели), `precast_parapet` (парапеты), `precast_shaft` (шахты лифтов), `precast_vent` (вентблоки) — см. §4.5 |
| `template.py` | Разбор листа «ВОР КР_ЖС» (`parse_template` → `TemplateRow` с восстановленным контекстом: часть/раздел/подраздел/тип конструкции/геометрия, признак `parking` — часть «Автостоянка») и запись результата в копию шаблона (`render_template`) с переносом стилей и сохранением структуры; поиск файла шаблона с учётом Unicode-формы имени (`resolve_template_path`) |
| `elements.py` | Индексация элементов IFC из «сырого» дампа (`ElementIndex.from_raw_dump`), определение типа конструкции/части здания/марки бетона/геометрии/подтипа лестницы (`component`), выборка (`select`) и агрегация количественных характеристик (`aggregate`: объём, площади, периметр, длина, марки). Наименование группы элементов (`group_name` — `ObjectType`), марка бетона с показателями (`concrete_spec` — «В30, W8, F150»), толщина из наименования группы (`_group_thickness`, если QTO её не содержит) или из bbox-оценки (`QTO_bbox::Толщина_мм`), карта «группа → заголовок блока» (`group_names_by_geometry`, `geometry_group_name`). Особые правила классификации: стены с признаком «парапет» и **низкие стены кровли** (тип этажа «Кровля», высота ≤ 2 м) → `parapet`; **сборные** лестничные марши («сборн» в наименовании) → `precast`; **лестничные площадки** (`IfcSlab` с типом «Монолитная площадка» и наименованием родительской лестницы «… Landing N») → `stair`/`landing`; этаж маршей и площадок без заполненного «Этажа» берётся у родительской лестницы (`IfcStair`); плиты перекрытия 1-го этажа при наличии подземной части относятся к подземной части |
| `documents.py` | Разбор документов: арматура из ВОР застройщика (`extract_rebar` → `RebarData`) с привязкой строк к **разделу, блоку, толщине конструкции и подтипу лестницы** (`RebarRow.group/thickness/component`, `scope_rows`, `section_total`, `diameter_class`, `buckets`), наследование подтипа лестницы по строкам ВОР (`row_components` — «Лестничные марши …» → `flight`, «Лестничные площадки …» → `landing`, сопутствующие строки наследуют подтип), раскладка арматуры по категориям работ (`rebar_buckets`, `rebar_work_items`, `rebar_label`), общий список строк документов и поиск ресурса по наименованию (`Documents.lookup`), разбор ПОС/ПЗ/ПД существующими модулями сервиса (`load_documents`) |
| `builder.py` | Сборка ВОР: заполнение строк работ и ресурсов, приоритет источников (модель IFC; арматура — из ВОР застройщика; ВОР застройщика как источник прочих объёмов не используется), расчёт опалубки фундаментных плит по торцам (`_foundation_formwork_area` — периметр × толщина), разбивка по геометрии (заголовки блоков — наименования групп элементов модели), разделение работ и ресурсов лестниц по подтипу (марш/площадка), эмиссия **динамических** строк-ресурсов арматуры (по диаметрам и классам из ВОР застройщика) и бетона (по маркам модели) вместо статических строк шаблона, запись файла (`build_vor`) |
| `customer_vor.py` | Приведение ВОР заказчика (PDF) к структуре типового ВОР (`build_customer_vor`): обогащение строк заказчика контекстом (тип конструкции, часть здания, вид работы, геометрия, подтип лестницы `component`), сопоставление с подразделами шаблона, суммирование объёмов по блокам/секциям/этажам, разделение работ лестниц «марш»/«площадка», заголовки блоков — наименования групп элементов модели, динамические строки-ресурсы арматуры и бетона по данным заказчика |
| `manager.py` | Жизненный цикл задачи (`VorGenerationManager`): приём файлов, фоновая обработка (`threading.Thread`), статусы/прогресс, выдача артефактов; обогащение сырого дампа bbox-периметром/толщиной плит для расчёта опалубки фундаментных плит (`_enrich_slab_formwork`) |
| `__init__.py` | Экспорт `VorGenerationManager`, `build_vor` |

## 3. Пайплайн

Задача создания (`POST /api/vor-generation`) сохраняет файлы в
`outputs/<job_id>/` и запускает фоновую обработку:

1. **Сырой дамп модели IFC** (`progress 5`) — `ifc_raw_dump.dump_ifc_elements_raw`
   выгружает параметры всех элементов модели в `IFC_исходные_параметры.json`
   (+ `.xlsx`). Это единственный источник геометрии и количеств (QTO).
   Дополнительно **JSON-дамп** обогащается **bbox-периметром/толщиной плит**
   (`VorGenerationManager._enrich_slab_formwork` → `ifc_raw_dump._compute_formwork_bbox_quantities`):
   у части плит QTO не содержит `Perimeter`/`Depth` (неполная выгрузка Revit),
   и для расчёта опалубки фундаментных плит (периметр × толщина) периметр и
   толщина вычисляются из геометрии. Значения (мм) записываются в колонки
   `QTO_bbox::Периметр_мм` / `QTO_bbox::Толщина_мм` и читаются `elements.py`.
   Ошибка обогащения не прерывает задачу.
2. **Разбор документов** (`progress 35`) — `documents.load_documents`:
   - **ВОР застройщика** — детерминированный разбор таблиц
     (`doc_pdf_parser.extract_vor_rows`, без LLM): строки с разделами, позициями,
     наименованиями, единицами и объёмами («было»/«стало», приоритет — «стало»).
     Из них извлекается **арматура** (`extract_rebar`).
   - **ПОС/ПЗ** — `pd_parser.parse_pos_constants` (глобальные константы проекта,
     LLM при доступности); **ПД** — `doc_pdf_parser.parse_pd`.
     Ошибка разбора документа не прерывает задачу (пишется в лог).
3. **Приведение ВОР заказчика к типовому виду** (`progress 55`) — только при
   загруженном **PDF ВОР застройщика**: `customer_vor.build_customer_vor`
   переносит объёмы заказчика в структуру типового ВОР и сохраняет файл
   `ВОР_заказчика.xlsx` (см. §4а). Шагу передаётся путь к сырому дампу модели
   (`elements_json_path`) — для подстановки наименований групп элементов модели
   в заголовки геометрических блоков. Ошибка шага не прерывает задачу.
4. **Сборка ВОР** (`progress 70`) — `builder.build_vor`:
   - разбор типового шаблона (`template.parse_template`);
   - построение индекса элементов (`ElementIndex.from_raw_dump`);
   - заполнение строк (см. §4);
   - запись файла в копию шаблона (`template.render_template`).
5. **Сохранение результата** (`progress 100`) — статистика сборки в
   `vor_generation.json` (включая блок `customer` со статистикой приведения
   ВОР заказчика), статус задачи `completed`.

Обработка выполняется в фоновом потоке (`daemon`); интерфейс опрашивает статус
(`GET /api/vor-generation/<job_id>`). При перезапуске сервиса незавершённые
задачи помечаются статусом `error`.

## 4. Правила заполнения типового ВОР

### 4.1. Строки и их виды

Разбор шаблона классифицирует строки листа:

| Вид | Признак | Обработка |
|---|---|---|
| `part` | заголовок части здания («Подземная часть здания …») | определяет часть здания для последующих строк; копируется как есть |
| `section` / `subsection` | «Раздел N. …» / «Подраздел N. …» | определяют тип конструкции; копируются как есть |
| `block` | геометрический/блочный заголовок («Стены толщиной … мм», «Плита рампы») | задаёт блок строк и геометрическую группировку (§4.4) |
| `work` | целочисленный № п/п (`1`, `2`, …) | заполняется объёмом работы (опалубка, бетонирование, армирование…) |
| `resource` | дробный № п/п (`1.1`, `2.3`, …) | заполняется объёмом ресурса (бетон, арматура, материалы) |
| `variant` | строка без номера («-объемом до 5 м3») | заполняется как работа |
| `empty` | пустая строка | сохраняется для структуры |

Строки части здания **«Автостоянка»** (раздел «Раздел 5. Монолитные ж/б
конструкции. Автостоянка» и его подразделы, строки шаблона 327–428) **всегда
переносятся** в результат с сохранением структуры (`TemplateRow.parking`), но
**не заполняются**: объёмы по ним не рассчитываются, столбцы D/F остаются
пустыми. Если в проекте автостоянки нет, раздел просто остаётся незаполненным
(в обоих файлах — `Сформированный_ВОР.xlsx` и `ВОР_заказчика.xlsx`).

### 4.2. Приоритет источников объёма

1. **Модель IFC** — объёмы и площади групп элементов (QTO).
2. **Документы** (ПОС → ПЗ → ПД) — если в модели данных нет.

**ВОР застройщика не используется как источник объёмов** (из него берётся
только арматура, §4.3): работы и материалы, отсутствующие в модели IFC, в
типовом ВОР **не заполняются** из ВОР застройщика (например «Гидрошпонка»,
«Устройство холодного шва бетонирования», «Битумная мастика» остаются с
прочерком). Объём, не найденный ни в модели, ни в прочих документах,
**не заполняется** (прочерк).

### 4.3. Арматура — только из ВОР застройщика (динамические строки-ресурсы)

- Строки «Устройство арматурных стержней» и «Устройство арматурных каркасов»
  заполняются **исключительно** из ВОР застройщика; строки-ресурсы под ними
  формируются **динамически** — по фактическим диаметрам и классам арматуры
  заказчика, а статические строки шаблона («Арматура d=6 мм А240» и т. п.)
  под этими работами **заменяются**.
- Тоннаж подбирается по **разделу ВОР**, соответствующему подразделу шаблона
  (`mapping.vor_section_matches` — тип конструкции + часть здания), а при
  наличии в ВОР разбивки по толщине конструкции («… толщиной 1000 мм …») —
  дополнительно по **толщине геометрического блока** (`RebarRow.thickness`).
- Разнос арматуры по работам (`mapping.rebar_bucket`):
  - «Устройство арматурных **стержней**» ← строки «**Арматура класса …**»
    (продольная/поперечная арматура);
  - «Устройство арматурных **каркасов**» ← строки «**Арматурные выпуски …**»
    и «… каркасы …».
  Если для категории работы данных нет, а работы другой категории в подразделе
  отсутствуют, берётся другая категория (двойного счёта при этом не возникает);
  если вторая работа в подразделе есть, её ресурсы не подставляются.
- Наименование динамической строки — «Арматура d=<диаметр> мм <класс>»
  (`rebar_label`), нумерация — «N.k» в порядке диаметров; стиль берётся у
  строки-образца шаблона.
- Строки-ресурсы арматуры, **не** относящиеся к работам армирования
  («Устройство/установка закладных деталей» и т. п.), не заполняются из общего
  тоннажа раздела — иначе объём арматуры удваивался бы с работами
  «… стержней»/«… каркасов».
- Если арматура раздела распределяется между геометрическими группами и
  привязки к толщине в ВОР нет, тоннаж делится пропорционально объёму бетона
  группы — сумма по группам равна полному тоннажу раздела.
- Класс арматуры дочерних строк («D25», «D20», …) наследуется от родительской
  строки-арматуры **в пределах того же раздела и блока** ВОР (нумерация позиций
  повторяется в каждом разделе/блоке); родительская строка пропускается, если
  у неё есть дочерние.

### 4.4. Группировка по геометрии и заголовки блоков

Если подраздел начинается геометрическим заголовком, строки блока повторяются
для каждой геометрической группы элементов:

- «**Плита толщиной … мм**», «**Стены толщиной … мм**», «**Парапеты толщиной … мм**»
  → группировка по толщине;
- «**Колонны сечением ахb мм**» → группировка по сечению;
- «**Плита перекрытия площадью … м2**» → один блок, в заголовок подставляется
  суммарная площадь группы.

**Заголовок геометрического блока** (все такие блоки, включая «площадью … м2»)
формируется так (`builder._group_header`):

1. **наименование группы элементов модели** (`Element.group_name` — `ObjectType`,
   например «Фундаментная плита:ADSK_Бетон В30_1000 мм», «Базовая стена:ADSK_Бетон
   В30_200 мм»); если в группе несколько наименований — преобладающее;
2. если наименований в модели нет — текст шаблона с фактическим значением
   геометрии («Стены толщиной 200 мм», «Плита перекрытия площадью 271.7 м2»);
   при отсутствии данных вместо значения подставляется прочерк
   («Парапеты толщиной — мм»).

Толщина группы берётся из QTO (`Width`/`Depth`), а при их отсутствии — из
наименования группы элементов («…_200 мм», «…_1400мм»), поэтому элементы с
одинаковой толщиной собираются в один блок. Блочные заголовки шаблона без
геометрии («Плита рампы», «Стены рампы») переносятся в результат как есть.

### 4.5. Виды объёмов работ (`classify_work`)

| Вид | Источник объёма |
|---|---|
| `formwork` (опалубка) | площадь: стены — боковая площадь, плиты — площадь, балки/колонны — поверхность; **фундаментные плиты — только торцы (периметр × толщина)** |
| `concrete` (бетонирование) | объём бетона группы |
| `rebar` (армирование) | тоннаж из ВОР застройщика (по разделу) |
| `thermoliner` (термовкладыши) | площадь × толщина (только для подразделов плит) |
| `volume` (прочий объём) | объём конструкций группы |
| `hydro_area` (гидроизоляция) | площадь группы |
| `count` (шт.) | количество элементов группы |
| `backfill` (засыпка), `embedded` (закладные) | из документов (кроме ВОР застройщика) |

Штучный объём (`count`) заполняется только по подразделу с **распознанным типом
конструкции** (`row.element_kind`): без него выбирать «все элементы части
здания» нельзя, поэтому объём не заполняется. Отдельно различаются **сборные**
изделия: тип `precast` — это сборные **лестницы** (в модели — сборные лестничные
марши), а подразделы сборных стеновых панелей, парапетов, шахт лифтов и
вентблоков получают собственные типы (`precast_panel`, `precast_parapet`,
`precast_shaft`, `precast_vent`). Так, если в модели есть только сборные
лестничные марши, количество 258 шт. попадает **только** в подраздел «Лестницы
сборные», а не во все подразделы раздела «Сборные ж/б конструкции».

### 4.6. Ресурсы (`classify_resource`) и динамические строки

- **Бетон** — только из модели, по марке. Под работой «Бетонирование …» строки
  формируются **динамически** по фактическим маркам модели (`Element.concrete_spec`
  — «В30, W8, F150»; подпись — `mapping.concrete_label`): объём каждой марки —
  сумма объёмов элементов этой марки, строки упорядочены по убыванию объёма;
  статические строки бетона шаблона под этой работой заменяются. Если марки в
  модели не указаны — весь объём бетона группы показывается в первой строке
  бетона шаблона.
- **Арматура** — из ВОР застройщика, динамическими строками по диаметрам и
  классам (см. §4.3).
- **Прочие материалы** — поиск в документах, **кроме ВОР застройщика**
  (`Documents.lookup(..., exclude_sources=("ВОР",))`): сопоставление по основе
  слов (устойчиво к падежам), обязательное совпадение числовых параметров
  (диаметры, размеры) и порог по доле совпавших слов. Из ВОР застройщика
  берётся только арматура, поэтому его строки-материалы в типовой ВОР не
  переносятся.

Правила эмиссии динамических строк (`builder._fill_rows`):

- динамические строки формируются только для работ, по которым есть данные
  (арматура — раскладка `rebar_buckets`; бетон — марки модели);
- строка-работа получает суммарный объём своих динамических строк, а её
  статические строки-ресурсы того же вида (бетон/арматура) **не выводятся**;
- нумерация динамических строк — «N.k» (`N` — номер работы); порядок арматуры —
  по диаметру и классу; стили берутся у первой строки-ресурса нужного вида в
  блоке (или у первой строки-ресурса);
- остальные строки-ресурсы блока выводятся как прежде (с перенумерацией «N.k»),
  их объёмы не меняются.

**Лестницы: разделение работ маршей и площадок.** В подразделах лестниц
(`stair` — монолитные, `precast` — сборные) работы и ресурсы **маршей** и
**площадок** заполняются раздельно:

- подтип строки шаблона определяется по наименованию (`mapping.stair_component`:
  «… маршей» → `flight`, «… площадок» → `landing`) и **наследуется** следующими
  строками блока — работы арматуры после «опалубки лестничных маршей» относятся
  к маршам, после «опалубки лестничных площадок» — к площадкам;
- объёмы берутся из подмножества элементов с соответствующим подтипом
  (`Element.component`: полёты `IfcStairFlight` и лестничные площадки `IfcSlab`
  «Монолитная площадка» → `flight`/`landing`); арматура — из строк ВОР
  застройщика с тем же подтипом (`RebarRow.component`);
- благодаря этому бетон и арматура **не дублируются** между работами маршей и
  площадок, а «Устройство сборных железобетонных лестничных площадок» не
  получает количество сборных маршей.

**Бетон под каждой работой бетонирования.** Объём смеси (строка-ресурс бетона)
заполняется под **каждой** работой «Бетонирование …»: подбор марок ведётся по
подмножеству элементов этой работы, поэтому объём работы и суммарный объём её
строк бетона согласованы. Если марки бетона в модели не указаны, но объём
работы есть, весь объём показывается в первой строке бетона шаблона.

### 4.7. Структура файла

`render_template` формирует лист заново из строк результата: удаляет строки
данных и записывает их в исходном порядке, перенося стили, высоту строк,
значения колонок A/B/C/E из строки-образца шаблона. Числа объёма записываются
с форматом `0.00`.

## 4а. Приведение ВОР заказчика к структуре типового ВОР (`customer_vor.py`)

Отдельный шаг задачи (файл **`ВОР_заказчика.xlsx`**, `progress 55`): ВОР
заказчика (PDF) перегруппировывается в структуру типового ВОР. В ВОР заказчика
объёмы разбиты по **деформационным блокам, секциям и этажам**, а в типовом ВОР
группировка иная — **часть здания → раздел → подраздел → геометрический блок →
работы/ресурсы**. Шаг выполняет эту перегруппировку.

### 4а.1. Разбор и обогащение строк заказчика

Строки берутся детерминированным разбором (`doc_pdf_parser.extract_vor_rows`) и
обогащаются контекстом (`customer_vor.collect_rows`):

| Признак | Как определяется |
|---|---|
| объём | колонка «стало» (`volume_now`), при её отсутствии — «было» |
| часть здания (`part`) | по тексту раздела/блока: «подземн/подвал» → подземная, «этаж/надземн/типов/техническ/кровл» → надземная |
| тип конструкции (`kind`) | `mapping.detect_kind` по наименованию строки, затем по разделу; изоляционные материалы (праймер, мембрана, галтель…) → `insulation`; материалы деформационного шва (мастика, «Вилатерм», герметик, геотекстиль, плёнка, «ФЛЕКС», гидрошпонка, экструзионный ППС) → `seam`; «фундамент» → `foundation_slab` |
| вид работы (`category`) | по наименованию: опалубка / бетон / арматура / шов / изоляция / засыпка / закладные детали / штучная |
| геометрия | толщина («толщиной 200мм», «t=100 мм») или сечение («400х400») из наименования; для **закладных деталей** без толщины в наименовании она наследуется от строки блока/секции («… толщиной N мм …», как в `documents.extract_rebar`), чтобы позиция попала в нужный геометрический блок |
| ориентация | для гидроизоляции: «вертикальн/по периметру/стен подвала» → вертикальная, «горизонтальн/подготовк» → горизонтальная |
| подтип лестницы (`component`) | по наименованию строки («Лестничные марши …» → `flight`, «Лестничные площадки …» → `landing`); строки без подтипа («Опалубка», «Арматура класса …») наследуют его от ближайшей предыдущей строки с явным подтипом в пределах раздела и блока (`documents.row_components`) |

Категория «закладные детали» (`embedded`) определяется для строк в **тоннах** с
признаками металлопроката («закладн», «пластин», «уголок», «швеллер», «двутавр»,
«полос», «прокат», «листов») — так они не путаются с изоляционными материалами и
арматурой.

Материалы **деформационного шва** у заказчика идут под подзаголовками «Деформационные
швы в зоне бетонной подготовки / ФП / стен подвала», которые детерминированный
разбор не сохраняет (подзаголовок относится к предыдущему блоку), поэтому тип
конструкции `seam` определяется по **наименованию материала**
(`customer_vor._SEAM_WORDS`: «деф.шв», «деформационн», «мастика», «вилатерм»,
«герметик», «геотекстил», «пленк/плёнк», «флекс», «гидрошпонк»;
`_SEAM_TOKENS`: «ппс» — как отдельное слово). Благодаря этому материалы попадают
в подраздел «Устройство деформационного шва» типового ВОР, а не в подраздел
гидроизоляции. Все материалы шва заказчика находятся в одном блоке
(«Деформационный блок № …»), поэтому все однотипные подразделы «Устройство
деформационного шва» типового ВОР (в подземной части и автостоянке) получают один
и тот же объём — разбить его по зонам (подготовка / ФП / стены подвала) по данным
разбора невозможно.

Родительские строки, у которых есть дочерние (позиция `N` при наличии `N.k`),
пропускаются — объёмы не считаются дважды. Пропускаются только разделы, не
относящиеся к типовому ВОР: металлоконструкции, земляные работы
котлована/шпунта, МАФ (`customer_vor._SKIP_SECTION_WORDS`). Разделы
«**Фундаменты башенных кранов**» и подобные им **переносятся** — они относятся
к подразделу «Фундаментная плита» (тип конструкции `foundation_slab`), при
этом блоки различаются по толщине конструкции («Плита толщиной 1000 мм» /
«… 1400 мм»).

### 4а.2. Агрегация (главное отличие группировки)

Объёмы **суммируются по всем блокам/секциям/этажам** в пределах подраздела
типового ВОР (тип конструкции + часть здания): группировка заказчика
«схлопывается» к подразделам шаблона.

### 4а.3. Сопоставление работ и ресурсов

- **Арматура** — по разделам ВОР заказчика (`documents.extract_rebar`):
  строка-работа «Устройство арматурных стержней/каркасов» получает суммарный
  тоннаж своих динамических строк, а сами строки-ресурсы формируются
  **динамически** по фактическим диаметрам и классам ВОР заказчика с разносом по
  работам, как в §4.3 («… стержней» ← «Арматура класса …»; «… каркасов» ←
  «Арматурные выпуски …»).
- **Опалубка и бетонирование** — по виду работы и единице измерения
  (сумма строк соответствующей категории подраздела).
- **Бетон** — по марке (`parse_concrete_grade`), как в §4.6; строки бетона под
  работой «Бетонирование …» формируются **динамически** по маркам, найденным в
  наименованиях ВОР заказчика (`customer_vor._concrete_specs`). Работы, у которых
  единица измерения не м3 (или не задана), объём бетона не получают: например,
  «Устройство холодного шва бетонирования» (п.м.) — это длина шва, а не объём
  бетонирования. Такие работы не классифицируются как бетонирование вообще
  (`mapping.classify_work` распознаёт словоформы «шов/шва/швы/швов» и относит их к
  «прочим»), поэтому строка остаётся незаполненной, а не получает объём бетона
  подготовки.
- **Закладные детали** — по фактическим позициям ВОР заказчика (пластины,
  уголки и т. п.): строка-работа «Устройство/установка закладных деталей»
  получает суммарный тоннаж своих динамических строк, а сами строки-ресурсы
  формируются **динамически** с наименованиями заказчика
  (`customer_vor._embedded_specs`). Статические металлоресурсы шаблона
  («Прокат листовой …», «Уголок …») под этой работой заменяются.
- **Прочие работы и материалы** — сопоставление наименований по основе слов
  (устойчиво к падежам), обязательное совпадение числовых параметров
  (диаметры/размеры). Строка принимается, если совпало не менее двух значимых
  слов, или доля совпадений ≥ 0,6, или (для работ) совпало «ведущее» слово
  наименования; для ресурсов правило «ведущего» слова применяется только к
  коротким названиям (≤ 2 значимых слова). Для **работ** допускается
  сопоставление и при **другой единице измерения** (например, стяжка у
  заказчика в м3, а в типовом ВОР — в м2; галтель ЦПС у заказчика в м3, а в
  типовом ВОР — в м), но только при сильном совпадении наименований — это не
  порождает ложных совпадений вроде «гидрошпонка» ~ «гидроизоляция». Объём
  переносится как есть, без пересчёта единиц.
- **Явные соответствия наименований** (`customer_vor._NAME_ALIASES`) имеют
  **приоритет** над автоматическим сопоставлением: если для строки типового ВОР
  задано соответствие, объём берётся по нему. Так разрешены случаи, когда
  автоматический подбор даёт неверный результат из-за похожих наименований
  материалов: «Полиуретановый герметик» ← «Полиуритановый герметик
  «Технониколь»» и «Полиуретановая плёнка» ← «Полиуритановая пленка
  ТЕНХНОНИКОЛЬ 400мм» (иначе обе строки получали суммарный объём друг друга),
  «Усиливающий слой гидроизоляции» ← «Доп. г/и ТЕХНОЭЛАСТ ФЛЕКС 600мм».
- **Горизонтальная/вертикальная гидроизоляция** разделяются по названию
  подраздела шаблона и ориентации строки заказчика.
- **Лестницы** — работы и ресурсы **маршей** и **площадок** разделяются по
  подтипу строки (`CustomerRow.component`): у заказчика объёмы опалубки, бетона
  и арматуры маршей и площадок идут отдельными строками («Лестничные марши
  подвала …», «Лестничные площадки подвала …», «Опалубка»), сопутствующие строки
  наследуют подтип предыдущей строки в пределах раздела и блока. Благодаря
  этому опалубка/бетон/арматура маршей и площадок не дублируются между работами
  подраздела («Монтаж/демонтаж опалубки лестничных маршей» получает только
  опалубку маршей, «… лестничных площадок» — только опалубку площадок).

### 4а.4. Геометрические блоки

Блоки «Плита толщиной … мм», «Стены толщиной … мм» и «Колонны сечением ахb мм»
разворачиваются по фактическим толщинам/сечениям ВОР заказчика. Строки без
геометрии (арматура, опалубка) распределяются между группами пропорционально
объёму бетона группы; строки с нулевым объёмом в группировке не участвуют.
**Закладные детали** без толщины в наименовании наследуют её от строки
блока/секции (см. §4а.1) и попадают в соответствующий геометрический блок —
например, «Пластина t12» и «Уголок 76х76х6» из раздела «Фундаменты башенных
кранов» (плита толщиной 1400 мм) выводятся под блоком «… 1400 мм».

Заголовок блока формируется так же, как в §4.4: если для группы найдено
наименование группы элементов модели (`customer_vor._block_header`,
`ElementIndex.geometry_group_name` — для этого шаг получает путь к сырому дампу
`elements_json_path`), в заголовок подставляется оно («Фундаментная плита:ADSK_Бетон
В30_1000 мм»); иначе — текст шаблона с фактическим значением геометрии
(«Плита толщиной 1400 мм»), а при отсутствии данных — с прочерком.

### 4а.5. Результат

Файл `ВОР_заказчика.xlsx` — копия типового шаблона с заполненными столбцами
«Объем» (D) и «Обоснование объема работ» (F, ссылка «ВОР заказчика: <файл>»).
Строки без данных остаются с прочерком.

## 5. Используемые справочники и модули

- `data/Типовой ВОР по КР.xlsx` — типовой шаблон (лист «ВОР КР_ЖС»), только чтение;
- `src/services/ifc_raw_dump.py` — выгрузка сырого дампа IFC
  (`dump_ifc_elements_raw`) и bbox-оценка периметра/толщины плит
  (`_compute_formwork_bbox_quantities` — используется для расчёта опалубки
  фундаментных плит по торцам);
- `src/services/doc_pdf_parser.py` — детерминированный разбор ВОР
  (`extract_vor_rows`), разбор ПД (`parse_pd`);
- `src/services/pd_parser.py` — разбор ПОС/ПЗ (глобальные константы);
- `src/services/zero_step.py` — `classify_storey_type` (определение части здания
  по этажу и отметке);
- `src/services/vor_generation/customer_vor.py` — приведение ВОР заказчика к
  структуре типового ВОР (§4а).

Группировка элементов выполняется по данным модели (QTO, свойства
`ExpCheck_*`, марки бетона, толщины/сечения). Справочники МССК
(`elements_mssk_nested.json`, `materials_mssk_nested.json`,
`msck_elements_compact.json`) в текущей реализации **не используются** —
тип конструкции и часть здания определяются по IFC-классу, свойствам
и наименованию элемента; они оставлены как возможное расширение для
сопоставления по кодам МССК.

## 6. API

Префикс — `/ifc-vor`, авторизация — cookie-сессия (как у остальных `/api/*`).

| Метод и путь | Назначение |
|---|---|
| `GET /api/vor-generation` | Список задач формирования ВОР |
| `POST /api/vor-generation` | Создание задачи (multipart/form-data: `ifc` — обязательно; `vor`, `pos`, `pz`, `pd` — опционально). Ответ `202` — запись задачи |
| `GET /api/vor-generation/<job_id>` | Статус задачи (`status`, `progress`, `message`, `error`, `result`, `has_result`, `has_customer_vor`) |
| `GET /api/vor-generation/<job_id>/files/<filename>` | Скачивание файла (`?download=1`); допустимые имена: `Сформированный_ВОР.xlsx`, `ВОР_заказчика.xlsx`, `vor_generation.json`, `IFC_исходные_параметры.json` |
| `GET /api/vor-generation/<job_id>/preview/<filename>` | Предпросмотр XLSX-файла ВОР (`Сформированный_ВОР.xlsx`, `ВОР_заказчика.xlsx`) — таблица до 100 строк для модального окна: `headers`, `rows`, `totalRows`, `previewRows`, `isPreview`. Заголовок колонок ищется по строке с «Наименование работ» на листе «ВОР КР_ЖС» |

Статусы задачи: `processing` → `completed` | `error`.

## 7. Артефакты задачи

Файлы сохраняются в `outputs/<job_id>/`:

| Файл | Описание |
|---|---|
| `Сформированный_ВОР.xlsx` | Заполненный типовой ВОР (лист «ВОР КР_ЖС») — итоговый результат |
| `ВОР_заказчика.xlsx` | ВОР заказчика (PDF), приведённый к структуре типового ВОР (формируется только при загруженном PDF ВОР застройщика) — см. §4а |
| `vor_generation.json` | Статистика сборки: число строк, заполненных объёмов, элементов модели, тоннаж арматуры, разобранные документы; блок `customer` — статистика приведения ВОР заказчика |
| `IFC_исходные_параметры.json` / `.xlsx` | Сырой дамп параметров элементов модели |
| `<kind>_<имя>` | Сохранённые загруженные файлы (модель и документы) |

Запись задачи хранится в общем реестре `outputs/sessions.json`
(`session_type = "vor_generation"`), поэтому задача отображается в «Истории»
и может быть открыта повторно (`POST /api/session/<id>/restore`).

## 8. Веб-интерфейс

Вкладка **«Формирование ВОР»** (`#vorTab`, кнопка `switchTab('vor')`) содержит:

1. **Загрузка модели и документов** — модель IFC (обязательно) и ВОР/ПОС/ПЗ/ПД
   (перетаскиванием или выбором файла; поддерживаются PDF, XLSX, XLS).
   Кнопки: **«🚀 Сформировать ВОР»** (запуск новой задачи, доступна после выбора
   модели IFC) и **«🆕 Новая задача»** (сброс формы: очищает выбранные файлы,
   списки файлов, статус/прогресс/этапы, скрывает блок результата, снимает выбор
   в списке задач и удаляет запомненный `vorGenerationJobId` из `localStorage` —
   позволяет начать новую задачу без перезагрузки страницы).
2. **Статус** — статус, источник (модель и документы), прогресс-бар и
   **компактный список этапов** под ним: этапы появляются поочерёдно по мере
   выполнения (`Выгрузка параметров элементов модели IFC` → `Разбор загруженных
   документов` → `Приведение ВОР заказчика к типовому виду` → `Формирование ВОР
   по типовому шаблону` → `Запись файла ВОР`), будущие не показываются; по
   завершении добавляется итоговая строка «✓ ВОР сформирован».
3. **Сформированный ВОР** — итоговые файлы (блок показывается при завершении):
   «Сформированный ВОР» (`Сформированный_ВОР.xlsx`) и «ВОР заказчика»
   (`ВОР_заказчика.xlsx`, только при наличии) — каждый с просмотром в модальном
   окне («👁️ Просмотр», до 100 строк) и кнопкой скачивания.

Блок «Сохранённые задачи» со списком задач и кнопкой «Обновить» в интерфейсе
вкладки отсутствует: задачи открываются из общего списка сессий («История»,
кнопка «Открыть ВОР»). Сводная статистика и поясняющие строки в блоке
результата не отображаются (статистика сборки остаётся в `vor_generation.json`).

JS-функции: `setupVorGenerationUploads`, `createVorGeneration`,
`resetVorGenerationForm`, `openVorGeneration`, `pollVorGeneration`,
`loadVorGenerationJobs`, `restoreVorGeneration`.

## 9. Ограничения и допущения

- Объёмы заполняются только там, где есть данные: строки без данных остаются
  с прочерком (это ожидаемое поведение, а не ошибка).
- **ВОР застройщика не является источником объёмов** типового ВОР (из него
  берётся только арматура, §4.3): работы и материалы, отсутствующие в модели
  IFC, не заполняются (например «Гидрошпонка», «Устройство холодного шва
  бетонирования», «Битумная мастика»).
- Опалубка фундаментной плиты считается **по торцам** (периметр × толщина).
  Периметр берётся из QTO, а при его отсутствии — из bbox-оценки; bbox-периметр
  приближённый (для повёрнутых в плане плит может отличаться от фактического
  контура), поэтому значение может быть неточным.
- Тип конструкции и часть здания определяются по IFC-классу, свойствам и
  наименованию элемента; справочники МССК пока не задействованы.
- Разделы ВОР застройщика сопоставляются с подразделами шаблона по
  ключевым словам (`vor_section_matches`); при неоднозначности раздела
  арматура может не заполниться (прочерк).
- Если один и тот же набор элементов модели соответствует нескольким
  подразделам шаблона (например, «Плита перекрытия» и «Рампа» для
  `IfcSlab`/`IfcFooting`), объёмы могут дублироваться — структура типового ВОР
  не содержит привязки к зонам/захваткам.
- Разбор ПОС/ПЗ/ПД использует локальную LLM; при её недоступности
  соответствующие объёмы не заполняются (задача при этом завершается успешно).
- Приведение ВОР заказчика (§4а) поддерживается только для **PDF**-файла ВОР;
  сопоставление работ и материалов — эвристическое (по типу конструкции,
  части здания, виду работы и наименованию), поэтому часть строк может
  остаться с прочерком, а близкие по названию работы (например, два вида
  гидроизоляции в одном подразделе) могут получить одинаковый объём.
  Разделы ВОР заказчика, не относящиеся к типовому ВОР (котлован/шпунт,
  металлоконструкции, МАФ), не переносятся.
- Объёмы бетона и марок берутся из модели IFC (приоритет модели), поэтому
  марка/объём блока могут отличаться от данных ВОР заказчика для того же
  конструктивного элемента (в `ВОР_заказчика.xlsx` используются данные
  заказчика, в `Сформированный_ВОР.xlsx` — модели).
- **Опалубка лестничных маршей** в модели IFC не рассчитана: у полётов
  (`IfcStairFlight`) QTO содержит только объём и длину (площади опалубки нет),
  поэтому строка «Монтаж/демонтаж опалубки лестничных маршей» остаётся с
  прочерком. Опалубка лестничных площадок берётся из площади плит площадок.
- Подразделы **вертикальной гидроизоляции/теплоизоляции, деформационного шва и
  засыпки песком** подземной части заполняются только при наличии
  соответствующих элементов в модели; если таких элементов нет (в IFC их нет),
  строки остаются с прочерком (ВОР застройщика источником объёмов не является,
  §4.2).
- Часть здания **«Автостоянка»** всегда переносится в результат, но не
  заполняется: если в проекте автостоянки нет, раздел остаётся незаполненным
  (столбцы D/F пусты, §4.1).
- Рабочая директория — **копия сервиса**: изменения переносятся в основной
  (Docker) сервис вручную.

# Синхронизация README ↔ диаграмма бизнес-процесса

## Назначение

Диаграмма `Блок_схема_ВОР_и_IFC_—_бизнес_процесс_2.drawio` описывает
бизнес-процесс генерации ВОР. Источник истины — `README.md`:

- `README.md` — §1–9: карта проекта (обзор, режимы, функциональность,
  структура, стек, модели, хранилища, API, запуск);
- `README.md` — §10 «Режим ЦС (CS)» (ранее KR);
- `README.md` — §11 «Режим ИИ (AI)» (ранее AR);
- `README.md` — §12 «Режим Архитектура (ARCH)»;
- `README.md` — §13 «Проверка ЦИМ модели»;
- `README.md` — §14 «Типовые ВОР, сверка и сметная форма»;
- `README.md` — §15 «Сравнение ведомостей объёмов работ».

Задача скила — держать диаграмму в соответствии с README и **доказуемо**
показывать, что именно изменилось.

## Как устроено сопоставление (главное)

Раньше скрипт вытаскивал «сущности» эвристикой (все заголовки, первые колонки
таблиц, каждый идентификатор в backticks) и сравнивал их с подписями узлов
через `difflib`. Из-за этого в манифест попадали сотни мусорных сущностей и
появлялись ложные привязки (например, `Типовой ВОР по КР.xlsx` →
узел «Формирование ВОР по типовому шаблону»).

Сейчас сущности процесса выявляет **LLM проекта — Qwen3.8 (`qwen3.8:27b`)**
через Ollama, а сопоставление идёт **только по её комментариям**:

```
README.md
   │  readme_llm_blocks.py: детерминированная нарезка на блоки
   ▼
блоки (абзац / список / таблица / код + путь по заголовкам)
   │  промпт prompts/readme_blocks_prompt.md → Ollama (Qwen3.8)
   ▼
docs/readme-blocks.json: entities[{syncKey, kind, title, comment, aliases}]
   │  sync_check.py: сопоставление ТОЛЬКО по comment/aliases/title
   ▼
узлы .drawio (+ атрибуты syncKey/syncComment/syncAliases на узле)
```

Правила сопоставления (`sync_check.score_pair`):

1. `syncKey` узла совпал с `syncKey` сущности → 1.0 (стабильная привязка).
2. `title`/`alias` сущности **полностью** совпал с подписью узла → 0.97.
3. Пословное вхождение (подстрока не считается: «Форма» не цепляется к
   «Платформа»); алиас из служебных слов («режим», «этап», «обработка») не
   матчится; однословные алиасы короче 6 символов — только как полное
   совпадение → 0.62–0.95.
4. Алиас найден в закреплённом комментарии узла → 0.90.
5. Пересечение значимых слов `title`+`aliases` с подписью узла: минимум два
   общих слова и ≥60 % слов узла → 0.55–0.95. Морфология — без зависимостей:
   общий префикс ≥4 символов и ≥70 % короткого слова («стены» ↔ «стен»,
   «чертежа» ↔ «чертежей»).
6. Пересечение слов **комментария** LLM с подписью узла: ≥2 общих слова и
   ≥70 % слов узла → до 0.75 (самое слабое правило).

Порог по умолчанию — `--min-score 0.62`, разведение 1:1 (жадно, по убыванию
оценки). Никакого сырого текста README в сопоставлении нет.

Дополнительно:

- **контейнеры** (swimlane, рамки веток — те, внутри которых лежат другие
  узлы) по слабому правилу комментария не матчатся: крупная подпись иначе
  перетягивает случайные сущности;
- **оформление** (`style="text;…"` — заголовки страницы, подписи) в
  сопоставлении не участвует;
- **легенда** исключается файлом `docs/diagram-sync-ignore.json`
  (`ids` + `labels`), его правят вручную при изменении легенды;
- слабые привязки (score < 0.75) `bootstrap` печатает отдельным списком —
  их проверяют глазами, а не принимают на веру.

## Установка

KodaCode ищет навыки в `~/.koda/skills`, `~/.agents/skills`, `.koda/skills`,
`.claude/skills`, `.agents/skills`.

### Вариант A — локально для проекта (рекомендуется)

```bash
mkdir -p .koda/skills/vor-diagram-sync/{scripts,prompts,references,docs}
# скопируйте SKILL.md, scripts/, prompts/ и references/ в созданную папку
```

### Вариант B — глобально

```bash
mkdir -p ~/.koda/skills/vor-diagram-sync/{scripts,prompts,references,docs}
# то же содержимое
```

### Требования

- Python 3.10+ (только stdlib — `requests` не нужен).
- Доступная Ollama с моделью `qwen3.8:27b`. Настройки берутся из окружения
  или из `.env` проекта: `OLLAMA_BASE_URL` (в рабочей копии —
  `http://<host>:11450`, порт Docker-сервиса `ollama`), `LLM_MODEL`.
  Переопределение — `--base-url`, `--model`.
- Сам скрипт ничего не импортирует из `src/`, поэтому запускается системным
  `python3`.

## Рабочий цикл

Все команды выполняются из корня проекта, пути к скриптам — абсолютные.

### 1. Сущности README (LLM)

```bash
# только нарезка, без LLM (быстрая проверка блоков)
python3 "$SKILL/scripts/readme_llm_blocks.py" --split-only

# пилот на первых 14 блоках (проверка качества промпта)
python3 "$SKILL/scripts/readme_llm_blocks.py" --limit 14 \
        --out docs/readme-blocks-pilot.json --cache docs/readme-blocks-pilot-cache.json

# полный прогон (кеш: повторный запуск не дёргает LLM для неизменённых блоков)
python3 "$SKILL/scripts/readme_llm_blocks.py"
```

Результат — `docs/readme-blocks.json`:

```json
{
  "schemaVersion": 2,
  "model": "qwen3.8:27b",
  "readme": {"path": "README.md", "sha256": "…"},
  "entities": [
    {"syncKey": "cs-stage0-extract-ifc", "kind": "step",
     "title": "Извлечение элементов из IFC",
     "comment": "Этап 0 режима ЦС: zero_step разбирает IFC …",
     "aliases": ["Извлечение элементов", "Этап 0", "zero_step"],
     "evidence": "§10 Режим ЦС / 5.1. Этап 0", "line": 512}
  ]
}
```

`comment` и `aliases` — единственный источник сопоставления, поэтому при
ручной правке файла правьте именно их (и не меняйте `syncKey` без
необходимости: он держит привязку к узлу).

### 2. Первичная привязка

```bash
python3 "$SKILL/scripts/sync_check.py" bootstrap \
        --diagram "Блок_схема_ВОР_и_IFC_—_бизнес_процесс_2.drawio"
```

Печатает: сколько сущностей привязано, сколько без узла, сколько узлов без
сущности, и отдельно — «слабые привязки» (score < 0.75) для ручной проверки.
Манифест — `docs/diagram-sync.json` (схема v2, `entities` вместо `coverage`).

### 3. Закрепление комментариев на узлах

```bash
# сначала посмотреть, что будет записано
python3 "$SKILL/scripts/sync_check.py" annotate \
        --diagram "…drawio" --dry-run

# записать атрибуты и пересобрать манифест
python3 "$SKILL/scripts/sync_check.py" annotate --diagram "…drawio"

# дополнительно снять комментарии с узлов, чьи сущности исчезли из README
python3 "$SKILL/scripts/sync_check.py" annotate --diagram "…drawio" --prune
```

На узел пишутся атрибуты `mxCell` (вид диаграммы не меняется):

| Атрибут | Содержимое |
|---|---|
| `syncKey` | `syncKey` сущности |
| `syncComment` | комментарий LLM к сущности |
| `syncAliases` | алиасы через ` \| ` |
| `syncSource` | `evidence` (раздел/строка README) |
| `syncAt` | время простановки (UTC) |

После этого сопоставление становится детерминированным: `syncKey` совпадает →
score 1.0, дальнейшие переименования узла или правки README не сбивают
привязку.

### 4. Проверка актуальности

```bash
python3 "$SKILL/scripts/sync_check.py" check --diagram "…drawio"
```

Коды возврата: `0` — всё согласовано; `2` — есть изменения (отчёт в stdout);
`1` — нет манифеста или он старой версии. Отчёт содержит:

- README изменился после сборки сущностей → пересобрать `readme-blocks.json`;
- новые сущности (нет узла) — добавить узел или объяснить;
- исчезнувшие сущности — проверить, не устарел ли узел (скрыть, не удалять);
- изменившиеся комментарии — обновить атрибуты узла (`annotate`);
- изменившаяся привязка (узел был другим) — проверить вручную.

### 5. Фиксация после правки диаграммы

```bash
python3 "$SKILL/scripts/sync_check.py" stamp --diagram "…drawio"
python3 "$SKILL/scripts/sync_check.py" report --diagram "…drawio" --verbose
```

### 6. Валидация и рендер

```bash
python3 "$SKILL/scripts/drawio_io.py" validate "…drawio"
python3 "$SKILL/scripts/drawio_io.py" annotations "…drawio"   # что закреплено на узлах
```

## Железные правила

1. **README — истина, диаграмма — следствие.** Не добавляй в диаграмму то,
   чего нет в README.
2. **Сущности — только из `docs/readme-blocks.json`.** Не возвращай эвристику
   по заголовкам/backticks и не сопоставляй по сырому тексту README.
3. **Сначала diff, потом правка.** Никогда не перегенерируй диаграмму целиком:
   ручная раскладка — ценность, которую нельзя терять.
4. **Сохраняй `id` и геометрию** существующих ячеек. Новые `id` — только для
   новых ячеек; `id` удалённых не переиспользуй.
5. **Удаление = скрытие + changelog.** Ставь `visible="0"` и пояснение, а не
   удаляй ячейку: история должна оставаться прослеживаемой.
6. **Каждое изменение — с доказательством:** `syncKey`, `syncSource`
   (раздел/строка README), `id` ячейки.
7. **После правки — `validate` и `annotate`.** Без этого результат не готов.

## Файлы скилла

```
vor-diagram-sync/
├── SKILL.md
├── scripts/
│   ├── readme_llm_blocks.py   # README → блоки → Qwen3.8 → docs/readme-blocks.json
│   ├── sync_check.py          # bootstrap / annotate / check / stamp / report
│   └── drawio_io.py           # чтение/запись .drawio, атрибуты-комментарии
├── prompts/
│   └── readme_blocks_prompt.md  # промпт выявления сущностей (## SYSTEM / ## USER)
├── references/
│   ├── drawio-xml.md          # формат .drawio и атрибуты sync*
│   └── project-inventory.md   # что вообще должно быть на диаграмме
└── docs/                      # рабочие артефакты (в проекте — docs/)
    ├── readme-blocks.json       # сущности README (LLM)
    ├── readme-blocks-cache.json # кеш аннотаций по хешу блока
    ├── readme-blocks-raw.json   # нарезка без LLM (--split-only)
    ├── diagram-sync-ignore.json # узлы-легенда/оформление вне сопоставления
    └── diagram-sync.json        # манифест синхронизации (v2)
```

Манифест v2 (`docs/diagram-sync.json`) хранит **все** сущности: у привязанных
есть `cellId`/`score`/`method`, у непривязанных — `cellId: null`. Поэтому
`check` показывает только реальные добавления/удаления, а не весь список
заново.

## Кеш и стоимость

- Кеш — `docs/readme-blocks-cache.json`: ключ = хеш текста блока, значение =
  список аннотаций. Кеш сбрасывается автоматически при смене модели или
  промпта (хеш промпта хранится в файле).
- Полный прогон README (~4 тыс. строк, ~385 блоков) — 47 батчей, около
  30 минут на GPU. Повторный прогон после правки README обрабатывает только
  изменённые блоки (в этом проекте — 385 блоков → 19 блоков → ~3 минуты).
- Параметры батча: `--batch-chars 7000`, `--batch-blocks 12`,
  `--num-ctx 16384`, `--num-predict 4096`, `--timeout 600`.
- Если ответ модели обрывается (`LLM вернула не JSON`), запускайте добор с
  меньшим батчем и большим лимитом токенов:
  `--batch-blocks 5 --num-predict 8192` (готовые блоки берутся из кеша).
- `sync_check.py` работает за секунды: токены и морфология кешируются
  (`lru_cache`), поэтому 347 сущностей × 59 узлов считаются ~2 с.

## Диагностика

| Симптом | Что делать |
|---|---|
| `LLM недоступна (…)` | проверить `OLLAMA_BASE_URL` в `.env`; в Docker Ollama проброшена на `11450` |
| `LLM вернула не JSON` | уменьшить `--batch-blocks`/`--batch-chars` и поднять `--num-predict`, повторить (кеш сохранит готовое) |
| «Слабые привязки» в `bootstrap` | уточнить `aliases` сущности в `docs/readme-blocks.json` или поправить подпись узла, затем `annotate` |
| Сущность «без узла» | добавить узел в диаграмму либо расширить `aliases` (синонимы, имена файлов) |
| Ложная привязка | проверить, нет ли в `aliases` общих слов; после `annotate` привязка фиксируется по `syncKey` |
| Узел легенды попал в привязку | добавить его `id`/подпись в `docs/diagram-sync-ignore.json` |
| Узел потерял `sync*` после правки в draw.io | повторить `annotate`; привязка восстановится по алиасам/комментарию |

## Ограничения

- Режим 1:1: один узел — одна сущность. Если сущностей на узел больше,
  объедините их в `docs/readme-blocks.json` (один `syncKey`, общие `aliases`)
  или заведите отдельные узлы.
- README подробнее диаграммы: сущности вида `api`/`data`/`model`/`rule`/
  `module` (эндпоинты, справочники, модели, модули) обычно узлов не имеют.
  Отчёты делят «без узла» на **процессные** (`mode`, `stage`, `step`,
  `artifact`, `external`, `role`) и **детали реализации** — вторые для схемы
  процесса нормальны.
- Служебные и декоративные узлы (легенда, заголовки, «Режим?») остаются в
  `orphans` или в ignore-файле — это нормально, они не обязаны иметь сущность.
- `docs/*.json` — рабочие артефакты скила, их можно коммитить вместе с
  диаграммой: манифест и комментарии узлов должны версионироваться вместе.

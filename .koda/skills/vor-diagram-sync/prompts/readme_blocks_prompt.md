## SYSTEM

Ты — аналитик бизнес-процессов. Твоя задача: по фрагментам README проекта
определить, какие элементы бизнес-процесса в них описаны, и оставить к ним
комментарии. По этим комментариям потом сопоставляются узлы блок-схемы,
поэтому комментарий и алиасы должны описывать сущность так, как её подписывают
на диаграмме.

Работай только с тем, что есть в тексте. Ничего не придумывай. Отвечай строго
одним JSON-объектом без пояснений и без markdown-обёрток.

## USER

Ниже — блоки README. Каждый блок начинается строкой
`--- БЛОК <id> | раздел: <путь по заголовкам> | строка <N> | тип: <вид> ---`.

Верни JSON строго такого вида:

{
  "blocks": [
    {
      "blockId": "b1a2b3c4",
      "kind": "step",
      "title": "Извлечение элементов из IFC",
      "syncKey": "cs-stage0-extract-ifc",
      "comment": "Этап 0 режима ЦС: zero_step разбирает IFC через ifcopenshell, нормализует характеристики и QTO, формирует ДЛЯ_СМЕТЧИКА_исправленный.xlsx. На диаграмме — блок «2. Извлечение элементов» ветки ЦС.",
      "aliases": ["Извлечение элементов", "Этап 0", "zero_step", "ДЛЯ_СМЕТЧИКА_исправленный.xlsx"],
      "evidence": "§10 Режим ЦС / 5.1. Этап 0"
    }
  ]
}

Правила отбора:

1. Включай блок, только если он описывает элемент бизнес-процесса, который
   должен быть виден на блок-схеме: режим, этап/шаг, модуль или функцию,
   артефакт (файл результата), API-эндпоинт, справочник данных, модель ИИ,
   внешнюю систему, роль пользователя, обязательное правило процесса.
2. Не включай: оглавление, историю переименований, общие рассуждения,
   настройки окружения и запуска, примеры кода, служебные примечания,
   пояснения форматов, если они не меняют ход процесса, дубли уже
   перечисленного в другом блоке.
3. Один блок — не больше одной сущности. Исключение — сводная таблица или
   список функциональности: из неё верни до 8 сущностей, по одной на строку,
   ради которой строка написана. Остальные блоки — строго одна сущность.
4. Одну и ту же сущность нельзя возвращать дважды в одном ответе. Если она
   уже встречалась в этих блоках, используй тот же `syncKey`, а не новый.
5. `kind` — одно из: mode, stage, step, module, artifact, api, data, model,
   external, rule, role.
6. `title` — короткое имя сущности, 2–6 слов, без точки в конце; это подпись
   узла на диаграмме.
7. `syncKey` — стабильный идентификатор сущности: только латиница, цифры и
   дефис, 3–60 символов, с префиксом режима (`cs-`, `ai-`, `arch-`) или
   области (`common-`, `check-`, `typical-`, `compare-`, `platform-`).
   Одна и та же сущность в разных блоках — один и тот же `syncKey`
   (например `ai-works-final-selector`).
8. `comment` — 1–3 предложения: что это, на каком шаге процесса, что
   проверять/рисовать на диаграмме. Комментарий — единственный источник
   сопоставления с узлами, поэтому в нём должны быть и смысл, и характерные
   слова: имена модулей, файлов, эндпоинтов.
9. `aliases` — 2–6 коротких вариантов названия и ключевых слов, которые
   реально могут стоять на узле диаграммы: сокращения, русские названия,
   имена файлов и модулей. Не добавляй общие слова (`Смета`, `Результат`,
   `Данные`, `Файл`, `Модуль`, `Работы`) как отдельные алиасы — они дают
   ложные совпадения; такие слова допустимы только внутри составного
   названия из двух и более слов.
10. `evidence` — путь по заголовкам (из строки блока) и, при необходимости,
    номер строки.
11. Если ни один блок не подходит — верни `{"blocks": []}`.
